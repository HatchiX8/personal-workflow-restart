# 任務日誌蒐集與關聯

## 篩選日誌

1. 以 UTF-8 讀取 Workflow Root 的 `agent-workspaces/task-journals/` 下可存取 Markdown 檔。
2. 只採用 YAML frontmatter 中可解析且落在 `[start, end)` 的 `completed_at`。不得以檔案建立、修改或目錄時間判定是否納入。
3. 收集 `thread_id`、`mode`、`project`、`workstream`、`role`、`skills`、`status`，以及正文中的最終結果、工作影響、關鍵決策、取代做法、驗證、返工、阻礙與後續狀態。缺欄位、時間無法解析或內容不足時，保留限制，不猜測。

## 新舊格式相容

- 新格式日誌依 `project` 與 `workstream` 分組，再以「任務結果」判斷主要進展；不要用修改檔案數量或 Skills 清單代表工作主線。
- 舊格式日誌沒有 `workstream` 時，只能依任務目標、使用者決策與完成內容中直接可見的共同目的做保守分組。無法唯一判斷時保持獨立，並在附錄標記為舊格式缺欄位。
- 舊格式的「未完成項目」只有在內容明確屬於原始任務範圍時，才能轉成必要後續。像「尚未建立未確認的業務 API」這類刻意未擴大的範圍，不得自動成為下週優先事項；無法判斷時只保留為候選或資料限制。
- 舊格式的「返工、阻礙與預期差異」可作為返工或阻礙證據，但不能只因最後一次任務寫「無」就否定同一工作主線中較早日誌已證實的方案反轉。

## 補充與去重

- 日誌資訊不足時，才可用其 `thread_id` 唯讀讀取同一個可取得的 Codex thread，補充必要的範圍、結果或明確決策；若無法讀取，標示限制。
- 每份任務日誌與其為補充而讀取的同一 thread 只構成一個事件。先以日誌為主，thread 只補上日誌沒有的已確認事實，不能重複列為另一個成果或改善事項。
- 沒有日誌的對話事件以 thread ID、Turn／訊息時間與主題去重；相同事件在多個 Turn 出現時合併為單一事件並保留最直接的證據。
- 同一 `project` 與 `workstream` 中，後續日誌明確記錄「取代或限制」時，將新舊日誌視為同一工作主線的決策演進；週報在「返工與學習」描述反轉及可證實原因，不把被取代方案繼續列為目前成果。
- `project: unknown` 或 `workstream: unknown` 不得僅靠技術名稱相似就合併到已知群組。只有目標、工作對象、時間與決策證據足以支持時才關聯。

## 後續事項判定

- `必要後續` 可以成為未完成或下週候選，但仍須依週報規則判斷重要性；它不會自動成為下週優先事項。
- `候選延伸` 只代表可選方向，不表示使用者已承諾執行。除非另有明確優先級證據，僅能放在附錄或候選事項。
- 「是否影響本次完成：是」應與 `partial` 或 `blocked` 一致。若日誌同時標示 `completed`，將其列為 metadata／正文不一致，不替來源修正結論。

## 跨來源關聯

ChatGPT 討論與 Codex 任務同時符合下列條件時，才可關聯為同一事件或前後因果：

- 專案或工作對象一致；
- 主題或任務目標一致；
- 時間順序與範圍合理；
- 有明確、可讀取的決策、thread ID 或其他直接證據支持連結。

只有名稱相似、時間接近、推測使用者意圖或一般主題相同，都不足以強制關聯。證據不足時保留分開事件，並避免暗示因果關係。
