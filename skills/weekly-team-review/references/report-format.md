# 週報格式與寫作規則

每份報告使用 UTF-8 Markdown。預設讀者是使用者本人，正文目標是在約 5 分鐘內完成閱讀並決定下週重點；完整來源、識別資訊與資料限制集中於附錄。

正文以工作主線和決策價值排序，不以日期、日誌數量或工具來源排序。目標長度為約 800～1200 個中文字；資料較多時優先合併次要事項，正文通常不超過 1600 個中文字，附錄不計入。

```markdown
---
report_start: "[start]"
report_end: "[end]"
generated_at: "[generated_at]"
---

# 每週工作回顧

> 本週一句話：[用 1～2 句說明整週最主要的進展、目前到達的狀態，以及必要時的主要風險。]［E01］

## 本週主要進展

### [工作主線或成果名稱]

- 完成結果：
- 為什麼重要：［E02］

## 重要決策

- 決定：
  - 原因：
  - 後續影響：［E03］

## 返工與學習

- 發生什麼：
  - 可證實原因：
  - 下次調整：［E04］

## 人機協作觀察

- 值得保留：
- 需要調整：［E05］

## 下週優先事項

1. [行動]
   - 為什麼現在做：
   - 完成標準：［E06］

## 附錄：範圍與資料涵蓋

- 實際起訖：[display_start, display_end)，Asia/Taipei
- 產生時間：[display_generated_at]
- 已讀取來源：
- 限制、遺漏原因與可能影響：

## 附錄：證據索引

- E01
  - 來源類型：ChatGPT／Codex 對話／Codex 任務日誌
  - 來源名稱：
  - Thread ID／日誌檔名：
  - Turn ID：
  - 時間：YYYY-MM-DD HH:mm
```

- `report_start`、`report_end` 與 `generated_at` 必須使用含 `+08:00` offset 的標準 ISO 8601 時間並保留 `T`。`report_end` 是保存期限清理的唯一時間依據，不得以檔名或檔案修改時間替代。
- YAML frontmatter 以外，所有供人閱讀的日期時間都使用 `YYYY-MM-DD HH:mm` 或同樣以半形空格分隔日期與時間的格式，不顯示 `T`；時區不明時不得自行補造。
- 正文不得直接顯示來源名稱、完整 thread ID、turn ID、UUID 或詳細時間。相關段落末尾只使用 `［E01］`、`［E02］` 等短代碼，完整資訊集中於附錄。
- 「證據索引」只列正文實際引用的證據。ChatGPT 證據保存來源名稱、完整 thread ID、必要的 turn ID 與時間；任務日誌證據保存可讀名稱、完整日誌檔名與 `completed_at`。同一證據被多處使用時沿用同一短代碼，不重複建立索引。
- Turn ID 僅在可取得且有助於定位特定訊息時保存；無法取得或無實際定位用途時填「未提供」，不得補造。
- 「本週主要進展」依工作主線整理 3～5 項；同一主線中的設定、重構、文件與驗證合併描述，不逐一列出所有任務。
- 「重要決策」、「返工與學習」與「下週優先事項」各自最多 3 項。「人機協作觀察」最多各 2 項；沒有足夠證據時保留標題並寫「本週沒有足夠證據形成觀察」。
- 「可證實原因」只寫來源明確支持的原因；只能推測時改寫為「尚未確認原因」，不要用建議代替原因。
- 同一事件只能在最能說明它的主要區塊完整敘述。其他區塊需要引用時，只說明它如何影響該區塊，不重述事件細節。
- 資料涵蓋限制放在附錄。只有當限制足以改變正文結論時，才在「本週一句話」以一句話提醒。
- 使用者明確要求稽核或完整證據報告時，可在附錄增加來源統計、排除理由與更多證據細節；正文仍維持相同章節順序。
- 報告只提出下週優先事項或候選事項；不得自行改寫長期規則、Workflow、角色規則或其他 Skill。
