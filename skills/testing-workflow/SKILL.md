# Testing Workflow

選擇能證明本次需求成立的最小測試集合，保留實際執行證據，並清楚回報未驗證範圍。不要把「執行了指令」等同於「功能已正確」。

## 確認輸入

1. 確認要驗證的需求、Bug、變更或使用者流程。
2. 確認目前角色與允許的操作：
   - Developer：可在任務範圍內新增或修改必要測試，並在修正後重新驗證。
   - Review：只能檢查測試內容、執行驗證與回報 findings。
   - 無角色：不得修改工作專案，只能規劃或執行安全的既有驗證。
3. 從 Project Config 與 repository evidence 取得可用的測試、Lint、Type Check、Build 與啟動指令。
4. 確認測試需要的環境、資料、帳號、網址與外部服務。缺少必要條件時，不猜測結果。

## 選擇驗證方式

依本次風險選擇最小必要集合，不要求每次執行所有層級：

- 純函式、資料轉換或商業邏輯：Unit Test。
- 多個模組、API、資料來源或服務互動：Integration Test。
- 關鍵使用者流程：E2E Test 或瀏覽器驗證。
- UI、互動、路由與狀態呈現：瀏覽器驗證。
- 無法可靠自動化的行為：列為人工驗證。

測試案例依需求選擇正常流程、邊界值、空值、無效輸入、錯誤處理、狀態切換、重複操作、非同步競態、權限與回歸案例。優先驗證輸入、輸出、資料狀態與使用者可觀察行為，不過度綁定內部實作細節。

## 執行順序

由快到慢執行適用項目：

1. 重現原始問題，或先確認需求的可觀察結果。
2. 執行與變更直接相關的單一測試。
3. 執行相關測試檔案或模組。
4. 執行適用的 Type Check 與 Lint。
5. 執行相關 Integration Test。
6. 執行 Build。
7. 必要時執行 E2E Test、瀏覽器驗證或人工驗證。

不得寫死測試指令。只使用 Project Config 或 repository evidence 明確證實可用的指令，並限制在本次任務相關範圍。

## 瀏覽器驗證

只有任務需要 UI、互動或完整使用者流程，且目前環境提供瀏覽器或 MCP 工具時，才執行本節。

1. 確認測試網址、環境、帳號狀態與必要前置資料。
2. 確認頁面能載入，並記錄初始狀態。
3. 依需求執行最小操作流程，每個步驟只做驗證所需動作。
4. 驗證顯示文字、表單結果、狀態切換、URL、錯誤訊息與其他可觀察結果。
5. 工具支援時，記錄必要的截圖、Console 錯誤或 Network 失敗。
6. 不在正式環境執行付款、購買、刪除資料、發送訊息或其他不可逆操作。
7. 不使用、輸出或保存未經授權的帳號與敏感資訊。

瀏覽器工具不存在、頁面無法存取或缺少登入狀態時，繼續其他可用驗證，並把瀏覽器驗證列為未執行。不得模擬不存在的工具結果。

## 處理失敗

將失敗分類為：

- 本次修改造成。
- 測試案例本身錯誤。
- 已存在的失敗。
- 環境或依賴問題。
- 疑似 Flaky Test。
- 原因尚未確認。

保留失敗指令、關鍵錯誤與必要環境條件。不得為了讓測試通過而降低斷言、刪除案例、隱藏錯誤或改變需求。

## 回報格式

```markdown
## 測試範圍

- 驗證目標：
- 主要風險：
- 選擇的驗證方式：

## 執行結果

- 通過：
- 失敗：
- 未執行：

## 瀏覽器證據

- 操作流程：
- 實際結果：
- 截圖或錯誤證據：

## 未確認事項

- 項目：
- 原因：
- 可能影響：
```

沒有使用瀏覽器時省略「瀏覽器證據」。沒有未確認事項時明確寫「無」。
