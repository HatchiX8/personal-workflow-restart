## Engineer Summary

lunch 模組是內部系統中的午餐活動前端功能。側邊選單只露出「午餐活動」入口，進入 `LunchChoice` 後由使用者選擇查看餐廳菜單、發起/參與訂餐活動，或使用轉盤抽午餐。模組主要由四個 page component 加一個 lunch API client 組成。

後續修改通常會碰到 `src/pages/LunchPage.jsx` 的餐廳 CRUD 與圖片上傳、`src/pages/OrderLunchPage.jsx` 的訂餐活動/總訂單/付款狀態 flow，或 `src/pages/LunchLotteryPage.jsx` 的抽選 UI。最需要小心的邊界是 `/api/lunch` 系列 API contract、`imageBase64` 圖片路徑組合、`userId` route param、`lunchStatus` 狀態值，以及 Ant Design Form 欄位名稱和後端期望欄位是否一致。

本 context 狀態為 PARTIAL，原因是前端邊界明確，但後端 contract 只能由前端使用方式推論。

## 資料流與 Contract

### Route 與入口 flow

1. 使用者從 sidebar 點擊「午餐活動」進入 `/system/:userId/lunch-choice`。
2. `LunchChoice` 檢查 localStorage `accessToken`；有 token 則開啟選擇 modal，否則導向 `/login`。
3. 選項 `lookup` 導向 `/system/:userId/lunch`；`postevent` 導向 `/system/:userId/order-lunch`；`lottery` 導向 `/system/:userId/lunch-lottery`。

可信度：明確可由檔案確認。來源：`src/pages/LunchChoice.jsx`、`src/routes/System.js`。

### API client contract

`src/actions/lunch.js` 封裝下列 API，皆從 localStorage 取 `accessToken` 並送 `Authorization: Bearer <token>`，成功時回傳 `res.data.data`，失敗時 throw `Error(error.response?.data?.message || error.message || "An error occurred")`。

| 函式 | 方法與路徑 | 前端用途 | 可信度 |
| --- | --- | --- | --- |
| `getAllLunch()` | GET `/api/lunch` | 取得餐廳/菜單清單 | 明確可由檔案確認 |
| `deleteLunch(data)` | DELETE `/api/lunch/:id` | 刪除餐廳 | 明確可由檔案確認 |

### 餐廳資料 shape

前端使用的餐廳欄位包含：`id`、`restaurantName`、`description`、`address`、`phoneNumber`、`imageBase64`。`LunchPage` 使用表格呈現並以 `imageBase64` 組合 `${axiosConfig.defaults.baseURL}${record.imageBase64}` 顯示菜單圖。

新增/編輯餐廳時使用 `FormData`，欄位包含：

- `data`: `JSON.stringify(values)`，form values 使用 `restaurant`、`depiction`、`address`、`phone`、`imageBase64`
- `imageBase64`: 上傳檔案物件，僅 JPG/PNG 且小於 3MB
- URL：POST `/api/lunch/lunch/<YYYYMMDDHHMM>-create`，PATCH `/api/lunch/lunch/<YYYYMMDDHHMM>-edit/:editId`

可信度：前端送出的格式明確可由檔案確認；後端如何轉換 `restaurant`/`depiction` 到 `restaurantName`/`description` 為待人工確認。

### 訂餐活動與總訂單 shape

訂餐活動列表使用欄位：`id`、`createdAt`、`restaurantName`、`description`、`address`、`phoneNumber`、`employeeName`、`imageBase64`。建立活動時，前端從 `allOrderData` 以 `restaurantId` 找出 `restaurantName`，送出 `{ restaurantId, restaurantName, userId }`。

使用者點餐送出資料包含：`restaurant`、`meals`、`quantity`、`totalPrice`、`remark`、`userId`、`lunchRestaurantId`、`lunchStatus: "NOPAID"`。

總訂單顯示欄位包含：`id`、`createdAt`、`restaurantName`、`quantity`、`meals`、`totalPrice`、`remark`、`employeeName`、`lunchStatus`、`lunchRestaurantId`。付款確認透過 `editOrderLunch(id, { ...record, lunchStatus: "PAID" })` 更新。

可信度：明確可由 `OrderLunchPage.jsx` 欄位與提交資料確認；後端是否接受完整 record PATCH 為待人工確認。

### 抽午餐 flow

`LunchLotteryPage` 使用 `getAllLunch()` 取得餐廳清單，將每筆資料轉為 `react-custom-roulette` 的 `{ option: restaurantName, style }`。點擊開始時以 `Math.random()` 產生 `prizeNumber`，停止後用 `alert` 顯示選中的餐廳。

可信度：明確可由檔案確認。

## 狀態、錯誤與副作用

- Auth gate：四個 lunch 頁面主要以 localStorage `accessToken` 判斷是否導向 `/login`；沒有細緻 permission denied UI。可信度：明確可由檔案確認。
- Loading：刪除確認 modal 使用 `useTransition` 的 `isPending` 作為 OK button loading；API fetch 與 submit 沒有獨立 loading state。可信度：明確可由檔案確認。
- Empty：`LunchLotteryPage` 在餐廳清單為空時顯示「尚無餐廳資料，請先新增餐廳！」；`LunchPage` 與 `OrderLunchPage` 主要依 Ant Design Table 空狀態。可信度：明確可由檔案確認。
- Error：多數 API catch 會 `toast.error(...)` 並 `console.error`；部分刪除 flow 會依 `error.response.status` 顯示 404/403/其他訊息，但 `actions/lunch.js` throw 的是一般 `Error`，不保證保留 `response`。可信度：根據結構推論。
- Success：新增/更新/刪除/點餐/付款確認多以 toast 顯示，部分成功後會重新 fetch 列表或總訂單。可信度：明確可由檔案確認。
- Stale data：`OrderLunchPage` 使用者點餐成功後只關 modal、reset form、toast，沒有重新 fetch 活動列表或總訂單；若總訂單 modal 已開啟與資料同步規則需人工確認。可信度：根據結構推論。
- 圖片副作用：餐廳新增/編輯會產生 `fileId` 並上傳 `FormData`，顯示端依 `axiosConfig.defaults.baseURL + imageBase64` 組 URL。後端儲存路徑與檔案替換規則未確認。可信度：待人工確認。
- 日期副作用：訂餐活動表格用 `createdAt < today` 加上 `pointer-events-none` 反灰舊活動，可能影響舊活動所有按鈕互動。可信度：明確可由檔案確認；產品規則待人工確認。
